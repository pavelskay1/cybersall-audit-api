# Наблюдения по cybersall (из аудитов 2026-09-23)

Зафиксировано для последующей доводки cybersall до "идеала". Не блокирует текущую работу.
Источник: аудиты crypto_backend.py через /api/audit/ensemble (2 прогона).

## 9. Деплой после доаудита всех модулей — [ВЫПОЛНЕНО 2026-09-23]
Все три модуля (orchestrator, sanitizer, main) прогнаны через /api/audit/ensemble,
найденные P0/P1/P2 внесены в финальные версии, развёрнуты на S2 с бэкапами.
- **orchestrator.py**: аудит ensemble_756cf500960e. Фиксы: универсальный fallback
  для всех стадий (claude-opus-5→kimi-k3, gpt-6-astra→deepseek-v4.1-flash,
  кimi-k3→deepseek-v4-pro), fail-closed quality_check, `_fallback_blocks` при отказе
  сплиттеров, harden_code на history/rework_prompt, фильтр пустых previous,
  try/except на fut.result(), MAX_TEMPLATE_SOURCE=50000, MIN_TEMPLATE_LEN=1000,
  STAGE_WORKERS=4, estimate с учётом параллелизма.
- **main.py**: аудит ensemble_38ab58d5afeb. Фиксы: P0-1 (HTTPException 413 — убран
  третий позиционный аргумент=headers), P0-2 (path traversal через model — добавлен
  `_validate_model`), P1-2 (partner stats key_hash[:8] префикс), P1-3 (admin key
  через hmac.compare_digest), P1-1 (tripwire-контроль в /api/audit/email),

- **sanitizer.py**: аудит ensemble_568cc83e38db. Фиксы: P1-1 (PEM backref \1 →
  незахватывающие группы, ловим PKCS#8 и оборванные PEM), ssh-паттерн больше не

  маскируются только если это НЕ идентификатор-переменная (api_key = api_key

- Верификация на проде: quality_ok=True на чистом коде, False на коде с багами;

  временный pro-ключ удалён.

Пункты 1-8 сведены внизу (правки повторять не требуется).

## 1. quality_ok=False при полном отчёте  — [ИСПРАВЛЕНО 2026-09-23]
Оба прогона вернули quality_ok=False, хотя отчёт был содержательным и дирижёр
отсеял ложные срабатывания. Дирижёр слишком строг: срабатывает на P0/P1-находках,
даже если они подтверждены и зафиксированы в шаблоне. Стоит уточнить критерий:
"высокое качество" = консистентность/полнота ответов моделей, а не факт наличия
багов в аудируемом коде.
Правка (orchestrator.quality_check): в промпт добавлено явное правило "quality=high,
если модели нашли ПОДТВЕРЖДЁННЫЕ баги и корректно описали их"; качество оценивается
как полнота/достоверность/консистентность, а не факт наличия багов в коде.

## 2. Шаблон кода собирает не все исправления из отчёта — [ИСПРАВЛЕНО 2026-09-23]
P1-1 (clientOrderId, retryable=False) и часть P2-валидаций в шаблон не попали,
хотя в отчёте значатся как рекомендации. Дирижёр монтирует шаблон частично.
Нужно правило: "каждая рекомендация из отчёта обязана быть отражена в шаблоне"
(список следования) либо увеличить max_tokens и повторить просьбу.
Правка (orchestrator.final_verdict): дирижёру дан пункт 7 — "СПИСОК СЛЕДОВАНИЯ":
перед секцией шаблона пронумерованный перечень ВСЕХ рекомендаций (P0/P1/P2) с
отметкой, что каждая внесена в шаблон; рекомендация без внесения = недочёт отчёта.

## 3. Дублирование кода и скобки в шаблоне — [ИСПРАВЛЕНО 2026-09-23]
Шаблон 297 строк при оригинале 244 — раздувание (добавлены комментарии FIX).
Допустимо, но стоит нормировать: шаблон должен быть изменением оригинала,
а не переписыванием с нуля (совпадение 70.6%).
Правка (orchestrator.final_verdict): пункт 6 переписан — "шаблон = ТОЧЕЧНО правленный
оригинал: сохраняй структуру, отступы, комментарии, имена, стиль; строки, не требующие
правок, оставляй без изменений".

## 4. Файл передаётся дирижёру только в final_verdict — [ИСПРАВЛЕНО 2026-09-23]
Дирижёр видит исходный код только на финальном этапе (мы добавили). Сплиттер и
quality_check исходник не получают — часть качества недооценена. Возможно стоит
давать дирижёру исходник с самого начала (для консистентности).
Правка (orchestrator.quality_check): добавлен параметр source_code — дирижёр получает
исходный код файла для сверки полноты/достоверности на этапе контроля качества.
Сплиттер исходник и так видит (он его разбивает).

## 5. P0-1: артефакт маскировки воспринимается как синтаксическая ошибка — [ИСПРАВЛЕНО 2026-09-23]
Санитайзер `api_key=..., secret=...` в сигнатуре __init__ искажал код до
непарсируемого вида, и все 3 модели подняли ложный P0. Фикс: санитайзер не
должен ломать сигнатуры (шаблон в отчёте был приведён к валидному виду, но
модели тратят силы на "P0 которого нет"). Рассмотреть: заменять значения
api_key/secret только после `=` при явных литералах, а имена параметров не трогать.
Правка (sanitizer): значение в паттерне api_key/secret/token теперь маскируется
ПОЛНОСТЬЮ вместе с кавычками/префиксом f-строки, голое значение — только из
безопасных символов до запятой/скобки/аннотации типа; атомарная группа + lookahead
не трогают `os.environ.get(...)`, типы (`: str = None`), имена параметров.
Проверено: `api_key=None, secret=None, password=None` и `os.environ.get(...)`
остаются валидными; f-string `g.api_key = f"{...}"` маскируется без поломки.

## 6. Шаблон не извлекается программно — [ИСПРАВЛЕНО 2026-09-23]
Клиенту приходится парсить секцию 'ШАБЛОН ИСПРАВЛЕННОГО КОДА' из markdown.
Предложение: выдавать шаблон отдельным JSON-полем `template_code` в ответе
/api/audit/* (помимо текста отчёта).
Правка (orchestrator.extract_template + audit_full + main.py): шаблон извлекается
из отчёта дирижёра (по секции + фолбэк на последний ```-блок) и возвращается в
resp `template_code`; main.py сохраняет его в reports/ensemble_*.template.py.

## 7. Долгий ответ (690s на 9KB файл) — [ИСПРАВЛЕНО 2026-09-23]
Аудит маленького файла занял ~11.5 мин (3 модели x блок + дирижёр). Для UX
стоит параллелить модели по блокам или кэшировать. Пункт на потом — сейчас
это не блокер.
Правка (orchestrator.audit_full): этапы (primary->deep->final) идут последовательно
(передача находок по цепочке), но все блоки одного этапа выполняются параллельно
(ThreadPoolExecutor, до 4 воркеров). Тест: 4 блока x 3 этапа за 0.44s вместо ~1.2s
последовательно. Для 1-блочных файлов выигрыш по времени отсутствует (как и было).
